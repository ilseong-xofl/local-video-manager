# Windows 배포 승인 체크리스트

이 문서는 Windows 설치 후보가 사내 배포 가능한지 판단하는 기준이다. 한 단계가 실패하면 다음 단계로 넘어가지 않고 같은 커밋에서 원인을 수정한 뒤 후보를 다시 만든다.

## 1. 후보 식별

- Git commit:
- package version:
- GitHub Actions run:
- artifact name:
- `Setup.exe` SHA-256:
- 테스트 일시:
- 테스트 담당자:
- Windows 버전과 장비:

후보는 `main`의 특정 commit에서 수동 `CI` workflow로 만든다. Actions artifact의 `SHA256SUMS.txt`와 내려받은 설치 파일의 해시가 일치해야 한다. 기존 GitHub Release와 같은 버전은 후보로 만들지 않는다.

Windows PowerShell에서 설치 파일 해시를 확인한다.

```powershell
Get-FileHash .\LocalVideoManager-win32-x64-Setup.exe -Algorithm SHA256
```

## 2. 자동 검증

- [ ] pull request의 macOS·Windows `pnpm check`가 통과했다.
- [ ] Windows `pnpm package`가 통과했다.
- [ ] pull request가 승인된 뒤 `main`에 병합되었다.
- [ ] `main`을 선택해 수동 `CI` workflow를 실행했다.
- [ ] `windows-candidate` 작업의 `pnpm check`가 통과했다.
- [ ] `pnpm make --arch=x64`가 통과했다.
- [ ] artifact에 `Setup.exe`, `RELEASES`, `*-full.nupkg`, `SHA256SUMS.txt`가 모두 있다.

## 3. 깨끗한 설치

- [ ] 기존 앱과 DB를 백업한 뒤 테스트 장비에서 기존 앱을 제거했다.
- [ ] Node.js나 FFmpeg를 별도로 설치하지 않은 Windows x64 환경에서 설치했다.
- [ ] 설치 중 표시된 Windows SmartScreen 또는 게시자 경고를 기록했다.
- [ ] 시작 메뉴에서 앱을 실행했다.
- [ ] 앱을 종료하고 다시 실행해도 정상 동작했다.
- [ ] 제거 후 재설치했을 때 기대한 사용자 데이터 유지 여부를 확인했다.

코드 서명 전 후보는 Windows 경고가 표시될 수 있다. 경고를 우회하는 방식은 후보 검수에만 허용하고, 사내 전체 배포 전에는 코드 서명을 별도 승인 기준으로 확인한다.

## 4. 핵심 기능

### 폴더와 목록

- [ ] 첫 실행에서 영상 폴더를 지정하고 최대 3단계 하위 폴더를 스캔했다.
- [ ] 새 영상을 추가한 뒤 다시 불러오면 새 항목만 등록되었다.
- [ ] 관리 폴더를 변경해도 이전 DB 정보가 유지되었다.
- [ ] 파일명에 한글·일본어·공백이 있는 C: 드라이브 경로에서 동작했다.
- [ ] 가능하면 D: 드라이브 또는 외장 디스크 경로에서도 동작했다.
- [ ] 파일 삭제·이동·수정 후 다시 불러왔을 때 목록과 DB 정책대로 표시되었다.
- [ ] 500~1,000개 표본 또는 실제 업무 폴더에서 스캔 시간과 화면 반응을 기록했다.

### 조회와 관리

- [ ] 썸네일과 모달 영상 재생이 동작했다.
- [ ] 제목 부분 검색, 태그, 반응, DB 등록일 범위, 정렬 필터가 동작했다.
- [ ] URL·캡션 등록/수정과 기존 영상 정보 복사가 동작했다.
- [ ] 태그 생성·수정·삭제와 다중 지정이 동작했다.
- [ ] 좋아요·싫어요 선택과 필터가 동작했다.
- [ ] `위치로 이동`이 Windows 탐색기에서 올바른 파일을 표시했다.
- [ ] URL 클릭이 기본 브라우저에서 열렸다.
- [ ] DB 백업 후 복원했을 때 정보·태그·편집 설정이 복구되었다.

### 영상 편집

- [ ] 편집 설정 생성·수정·삭제와 플랫폼 설정 저장이 동작했다.
- [ ] 9:16, 4:5, 1:1, 1.91:1에서 레터박스·크롭 미리보기가 올바르다.
- [ ] 검정·흰색·사용자 지정 레터박스 색상이 결과에 반영되었다.
- [ ] 텍스트 영역을 여러 개 추가하고 이동·크기 조절·순서 변경·삭제했다.
- [ ] 텍스트 프리셋 생성·불러오기·업데이트·이름 수정·삭제가 동작했다.
- [ ] 한국·일본·미국 권역별 폰트가 저장되고 다시 불러와졌다.
- [ ] `편집 영상 만들기`로 MP4가 생성되고 영상·음성이 정상 재생되었다.
- [ ] 생성 파일이 지정한 로컬 위치에 있으며 앱 재실행 후에도 원본과 설정이 정상이다.

### 운영 Service 연동

- [ ] 별도 `.env`나 실행 환경 변수 없이 설치 앱이 `https://lvms.ilscp.net`에 연결된다.
- [ ] 운영 계정으로 로그인하고 앱 접근 권한을 정상적으로 확인했다.
- [ ] 설정 메뉴에서 8~24자의 새 비밀번호로 변경한 뒤 자동 로그아웃되고, 새
      비밀번호로 다시 로그인했다.
- [ ] 사내 허용 IP에서 캡션을 생성하고 서버 기준 일일 사용량 `n/10`이 갱신되었다.
- [ ] 사외 IP에서는 로그인과 일반 앱 기능이 동작하고 캡션 생성만 차단되었다.
- [ ] Service 연결 실패 시 본 화면을 우회하지 않고 로그인 또는 접근 차단 상태를 유지했다.

## 5. 장애 상황

- [ ] 스캔 중인 파일이 다른 프로그램에서 복사 또는 사용 중이어도 앱 전체가 종료되지 않았다.
- [ ] 외장 디스크를 분리한 상태에서 오류를 확인한 뒤 다시 연결해 복구했다.
- [ ] 지원하지 않는 코덱 또는 손상된 영상 한 개가 다른 영상 처리를 막지 않았다.
- [ ] 긴 경로와 대용량 영상에서 실패 여부와 메시지를 기록했다.

## 6. 자동 업데이트

업데이트 검수에는 서로 다른 두 개의 공개 버전이 필요하다. 먼저 낮은 버전을 테스트 장비에 설치하고, 더 높은 버전을 GitHub Release로 게시한다.

- [ ] 낮은 버전 실행 시 더 높은 버전을 감지했다.
- [ ] 백그라운드 다운로드 후 `나중에`와 `지금 재시작` 선택지가 표시되었다.
- [ ] `나중에`를 선택하면 사용 중인 앱이 종료되지 않고 다음 실행에서 업데이트되었다.
- [ ] `지금 재시작`을 선택하면 앱이 재시작되고 업데이트되었다.
- [ ] 앱 버전이 높은 버전으로 변경되었다.
- [ ] 관리 폴더, SQLite DB, 태그, 편집 설정과 프리셋이 유지되었다.
- [ ] 진행 중인 편집/스캔 작업이 있을 때 `나중에`를 선택하면 작업이 중단되지 않았다.
- [ ] 업데이트 실패 후 앱을 다시 실행할 수 있었다.

공개 Release를 게시하면 기존 설치 앱도 업데이트를 감지할 수 있다. 따라서 업데이트 테스트 버전은 테스트 대상과 배포 영향 범위를 확인한 뒤 게시한다.

## 7. 배포 승인

- [ ] 차단급 결함이 없다.
- [ ] Windows 코드 서명 방식과 인증서가 준비되었다.
- [ ] 태그 Release에서 실제 배포할 `Setup.exe`를 다시 내려받아 설치·실행 smoke test를 통과했다.
- [ ] 2명 또는 3명의 사내 파일럿 사용자가 1일 또는 2영업일 실제 폴더로 사용했다.
- [ ] 파일럿에서 DB 백업을 확보했다.
- [ ] 설치 파일 SHA-256과 릴리스 노트를 사내 배포 공지에 포함했다.
- [ ] 문제 발생 시 배포 중단 담당자와 이전 설치 파일 위치가 정해졌다.
